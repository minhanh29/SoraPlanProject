NEW / INSIDE THE 66.096-SECOND CALL

Six responsibilities, one response.

The code sends one image and one instruction to Gemini and waits for a complete JSON response. The responsibilities below explain what that request asks the model to accomplish. They are not six separately observed API calls or a trace of the model’s internal execution.

Evidence boundary: 66.096 seconds is the measured client-side request timer. It includes SDK/client work, transport, and remote processing. No evidence divides it into individual perception, reasoning, or generation times. The numbering below is for explanation; the model’s internal task order is unknown.

What makes this a large request?


The instruction asks for every relevant component and precise coordinates in a single response. Each wall segment, room vertex, furniture box, type, label, angle, and confidence adds output. The model must also distinguish walls from cabinets, objects from text, and door openings from continuous walls. These requirements are documented in the prompt; their individual share of latency is not measured.

01 / SCOPE & EVIDENCE
Extraction is a single model request.


The model must locate the footprint, read dimensions, trace walls, identify objects, and outline rooms in a single response. Those are tasks described in the prompt, not separately timed model stages.


What was measured
Six completed Cloud Run jobs, all using cropped PNG images and gemini-4-argon. Each job has one extraction and two review calls. The latest run began around 21:32 ICT on 19 November.
Sample images are very similar: about 961–966 × 705–717 pixels and 147 KB. This is a narrow workload sample, not a benchmark across all plan types.
What the evidence cannot reveal
The logs do not capture the raw response JSON, exact wire request, deployed prompt text, first-token latency, thinking tokens, retry spans, or individual local operation timings.
The source file is locally modified. Request and prompt examples below reconstruct the current local implementation; they are not a verified copy of the deployed request.

Read the full extraction instruction from the local source snapshot
You are an architectural floor-plan digitisation engine.
Analyse the supplied floor-plan image and reconstruct its editable 2D geometry as structured JSON.
Your job is not to describe the image. Your job is to locate every meaningful architectural component precisely.

0. COORDINATES (READ CAREFULLY):
- Report ALL geometry in normalized image coordinates: integers from 0 to 1000, where [0, 0] is the top-left
  corner of the WHOLE image and [1000, 1000] is its bottom-right corner, independent of the image aspect ratio.
- Boxes are [ymin, xmin, ymax, xmax]. Points are [y, x]. Lines are [y1, x1, y2, x2].
- Do NOT convert anything to feet or meters; the server does that from "footprint_box_2d" and the real-world size.

1. FOOTPRINT & SCALE:
- "footprint_box_2d": the tight box around the OUTER faces of the exterior walls of the building.
- "width" / "height": the real-world size of that footprint, read from the overall dimension strings
  (e.g. 57'-0"). If only chained dimensions are given, add them up. If none are visible, estimate from standard
  sizes (interior doors ~3 ft / 0.9 m, queen bed ~5 x 6.7 ft). "units": "ft" or "m".

2. WALLS:
- Add all exterior walls ("exterior": true) and all interior partition walls ("exterior": false).
- "line" runs along the wall's CENTERLINE. Horizontal walls keep y1 == y2; vertical walls keep x1 == x2.
- "thickness" is the drawn wall thickness on the same 0-1000 scale, measured along the image width.
- Do NOT create door or window objects. Wherever a wall has a door or window opening, SPLIT the wall into
  separate segments before and after the opening and leave the opening as a blank gap.
- Connected walls must share endpoints exactly (corners and T-junctions meet).
- Only the thick drawn wall lines are walls. Cabinets, closets, shelving, counters and furniture outlines are
  NOT walls, even when drawn as small rectangles against a wall.

3. FURNITURE & FIXTURES:
- One entry per symbol actually DRAWN on the plan (each dining chair, each nightstand separately). Never one box
  around a group, and never invent items that are not drawn. Room names and dimension text are not objects.
- "box_2d" is the TIGHT box around the drawn symbol's outline as it appears in the image: its true drawn size,
  not a standard size, and excluding text labels, door swing arcs and nearby objects.
- L-shaped or U-shaped counters and sectional sofas: one box per straight run, so no box covers empty floor.
- Preserve the labels and adjacency of kitchen counter blocks, kitchen sink, stove and "Ref." (refrigerator).
  When contiguous top and left runs form a perpendicular corner along two walls, they belong to one
  L-shaped kitchen for subsequent 3D asset matching, rather than individual 3D assets. Keep their editable
  source boxes separate here; the placement stage combines their bounding footprint and corner orientation.
  A third parallel peninsula counter stays a separate standalone counter, even if it touches one of the runs.
- A rectangle drawn around a room name is a text frame, not furniture. Rugs are not furniture.
- Closets and wardrobes (drawn as a rail with zig-zag hanger lines) are "wardrobe" furniture: one box per run.
- "angle" is 0 for every object drawn parallel to the walls, whichever way it faces (the box already gives its
  extent). Only for objects drawn diagonally give the clockwise angle in degrees; box_2d is still the tight
  axis-aligned box around the drawn symbol.
- Every object lies inside the footprint.
- Objects never overlap: no two boxes on the same spot and no box on top of or inside another. A sink or stove
  set into a counter splits the counter into separate runs on either side of it.

4. ROOMS:
- "polygon": the room's inner wall faces as [y, x] points, clockwise. "name" comes from the plan label.
- "statedDimensions": the room's written size (e.g. 18' x 10') in real-world units when shown, else null.

If an object is uncertain, include it with a lower confidence score.

Return ONLY a valid JSON object matching this exact schema:
{

06 / OPTIMIZATION PLAN
Measure first. Then reduce model work.
The extraction call is the main target. Smaller local JSON operations cannot remove most of the 66-second wait.




01
Add spans and retain reproducible diagnostics.
First changeLow product riskNo direct speedup claimed
Add a job ID, call phase, review round, prompt hash, model version, and SDK version to each event. Time image inspection, prompt creation, client acquisition, request construction, API, JSON decoding, ID assignment, overlay drawing, normalization, and saving separately. Capture counts and full usage metadata, including thinking and cached tokens when available.
Use restricted, short-retention diagnostic storage for request/response bodies only when explicitly enabled. Keep routine logs limited to metadata. This enables real raw-versus-reviewed comparisons.
Exit criterion: reconcile each job’s child spans with its parent duration and explain slow review outliers. Do not infer thinking duration from output token count.


02
Benchmark model and reasoning settings.
Largest extraction opportunityBenefit unmeasuredQuality benchmark required
Test the current model against a lower-latency vision-capable model available in this project. Where the selected model supports it, compare lower thinking levels/budgets. Keep the image, task, and scoring fixed. The current wrapper sets no thinking configuration; it does not prove reasoning is disabled.
Start with 20 diverse plans × 3 repeated runs per shortlisted configuration. Include clean plans, scans, small text, irregular rooms, dense furniture, and ambiguous dimensions. Separate cold and warm calls; cap experiment spend before running.
Pass gate: valid JSON, retained wall/opening topology, object detection accuracy, box/polygon accuracy, scale accuracy, and no increase in serious placement errors. Promote only a Pareto improvement in latency, quality, and cost. Thinking configuration and usage metadata.


03
Reduce generated JSON without losing geometry.
Direct extraction changeBenefit unmeasuredOutput tokens are a hypothesis, not a proven cause
Trial a compact transport schema and expand it server-side into the existing editable plan. Move duplicated fields or safe defaults into local code only after checking downstream dependencies. Keep all coordinates, object distinctions, confidence needs, and scale information required for review.
Add an API response_schema for supported models and simplify prompt/schema duplication. JSON MIME mode alone does not declare the required fields. Schema constraints improve structural reliability; they do not guarantee geometrically correct output or lower latency. Avoid low token limits that truncate dense plans.
Do not add separate serial OCR, wall, room, and furniture model calls by default: extra request overhead may erase savings. Test a parallel decomposition only if independent outputs can be reconciled reliably. Structured output documentation.


04
Make the second review conditional.
Whole-pipeline improvementObserved removable call: 6.2–11.8 sAccuracy tradeoff
Start with one review plus deterministic geometry checks. Trigger a second review for unresolved warnings, invalid geometry, suspicious overlaps, or substantial first-round edits. Retain the existing stop-on-done behavior.
In the latest run, removing review 2 saves its 6.338 s model call before changed local overhead. Across six runs, the mean second-call duration is 8.865 s. These are counterfactual call savings, not verified end-to-end improvements. Five of six second reviews made edits; one made no changes.
Gate the change on a raw-versus-reviewed benchmark. Deterministic checks can detect invalid or inconsistent geometry; they cannot prove every image symbol is represented correctly. Check deployment too: the deploy script does not explicitly propagate PLAN_REVIEW_ROUNDS.


05
Remove repeat work and startup overhead.
Secondary optimizationCold wait observed: ~6–9 sCache hit rate unknown
For identical authorized inputs, cache a successful parse by image hash, crop and calibration settings, prompt/schema version, model configuration, and review policy. Scope reuse to the appropriate owner/project and invalidate on every relevant configuration change. Near-duplicate images in this sample do not prove an exact cache hit.
The SDK client is already reused after lazy initialization. Trial eager initialization and startup CPU boost. Compare keeping one Cloud Run instance warm against its ongoing cost. Removing startup can address the observed cold wait; it cannot remove the 66-second remote call. Cloud Run startup guidance.


06
Improve visible progress while latency work continues.
Perceived latencyNo model-compute saving assumed
Instrument a streaming variant to distinguish time to first content from response completion. Streaming may expose progress sooner, but does not itself establish a faster full response. Keep incomplete JSON out of the authoritative editor; optionally show a separate provisional preview.
Use real phase labels such as “Extracting geometry” and “Checking overlaps.” Current 65% and 80% progress values are fixed milestones, not time-based estimates. SDK streaming, response schema, and configuration reference.
